# Nonpaying challenge pilot persistence

The migration adds three empty private tables and four service-only RPCs. It
does not enable a pilot or change existing game, attendance, reward or payment
records. All RPCs revalidate the same Arcade wallet session inside the database.
Wallet/session binding does not establish a unique human or a prize identity.

The trusted service derives each legal move and result with the pinned game
adapter. The database stores that result atomically; it does not implement the
game engine. Browser clients have no table privileges or RPC execution rights.
An operator with database administrative access must insert a complete draft
configuration and explicitly enable it. The service role can read configuration
but cannot insert or activate one. A column-scoped `UPDATE(status)` grant lets
the service take PostgreSQL `FOR SHARE` configuration locks; a trigger rejects
every actual configuration mutation by that role. Enabled terms are immutable; they may only be
disabled, and a disabled configuration cannot be edited or reenabled.

## RPC signatures

- `arcade_challenge_pilot_load_config_v1(p_token_sha256 text, p_origin text,
  p_pilot_id text)` returns `null` when absent, or the indexed metadata plus
  `config`, `status`, `enabled`, UTC `serverNow`, and fixed nonpaying flags.
- `arcade_challenge_pilot_start_v1(p_token_sha256 text, p_origin text,
  p_pilot_id text, p_rules_hash text, p_attempt_token_sha256 text,
  p_seed_hex text, p_challenge_hash text)` creates a UUID `attemptId`. The token
  is generated by the trusted service; only its SHA-256 is stored. Expiry is the
  earliest of the pilot close, maximum attempt duration and session expiry.
- `arcade_challenge_pilot_load_attempt_v1(p_token_sha256 text, p_origin text,
  p_attempt_token_sha256 text, p_request_id uuid default null)` returns the
  internal attempt snapshot. With a request ID, `replay` is `null` or
  `{requestHash, expectedVersion, moveId, response}`. Existing records remain
  readable after the attempt cutoff while the original session is valid.
- `arcade_challenge_pilot_commit_move_v1(p_token_sha256 text, p_origin text,
  p_attempt_token_sha256 text, p_expected_version integer, p_request_id uuid,
  p_request_sha256 text, p_move_id integer, p_public_response jsonb,
  p_terminal boolean, p_result jsonb)` serializes commits with an attempt-row
  lock. It appends exactly one move and increments its version. Card IDs must be
  1–30; the service additionally checks the actual dealt/disabled cards. The
  hundredth move must end the attempt.

The internal attempt contains `attemptId`, `pilotId`, `rulesHash`, `adapterId`,
`adapterVersion`, `sourceHash`, `config`, `challengeHash`, `seedHex`, `wallet`,
`origin`, `sessionHash`, `startedAt`, `expiresAt`, `moves`, `version`, `status`,
`result`, `completedAt`, `serverNow`, the fixed nonpaying flags and `replay`.
It must not be returned wholesale to browser clients: the service projects the
approved public view and keeps the token hash, seed and session metadata private.

The commit RPC returns the stored public response. It overrides `attemptId`,
`version`, `attemptStatus`, `startedAt`, `expiresAt`, `completedAt`, `serverNow`
and `result` with database values, while preserving a service `status:'ok'`.
Terminal results receive the server completion timestamp. Both the result and
public response are bound to `mode:'nonpaying-pilot'`,
`identityScope:'wallet-session-only'`, `payable:false`, `prizeEligible:false` and
`awardsEnabled:false`. Contrary flags anywhere in the supplied JSON are rejected.

The same request ID, request hash, expected version and move ID returns the
**original** public response, even after completion or cutoff. Changed replay
inputs conflict. A new request with a stale version conflicts. An expired or
revoked session still fails; reauthentication creates a different session and
does not authorize retrieval or reuse of an old attempt. New moves at or after
the exclusive cutoff are rejected using the database clock after locking.
Each RPC explicitly locks the session row before revalidating it, serializing
revocation with writes. Starts also use a wallet/pilot transaction advisory lock
and permit at most twenty unexpired active attempts per wallet and pilot; a new
session for the same wallet cannot evade that cap.

## Concurrency validation boundary

Local tests execute the real migration and RPCs in the repository's pinned
PGlite dependency. This verifies SQL constraints, privileges, state transitions,
retry identity and failure behavior. PGlite uses one connection, so concurrent
JavaScript promises do **not** prove cross-connection PostgreSQL races. The
production mechanism is `SELECT ... FOR UPDATE` plus unique
`(attempt_id,request_id)` and `(attempt_id,expected_version)` constraints, all in
one RPC transaction. A hosted deployment still requires multi-connection
concurrency verification and current-schema review before enabling a pilot.
