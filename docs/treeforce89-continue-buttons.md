# TREE FORCE continuation buttons

The reported checkout switched to a transaction-ID recovery form as soon as wallet approval started. The client deliberately persisted an offer before signing, but the view interpreted that in-flight offer as a lost wallet response. That exposed manual recovery during the normal payment flow.

The dialog now distinguishes checkout, wallet approval, receipt verification and a confirmed payment. The primary actions are **Pay 20,000 TREE & restore lives**, **Check payment & continue** for an interrupted receipt, and **Resume gameplay · 3 lives** after authenticated server verification. Wallet approval shows a disabled waiting button and never renders a transaction input. The explicit Resume action hands the verified grant to the existing same-wave/same-score game resume path. A confirmed payment is retained until gameplay accepts the grant, so closing the dialog does not lose the receipt.

If wallet execution succeeded but its response was lost, automatic recovery reads recent transactions sent by the connected mainnet wallet through the pinned Sui SDK's Core API. Mainnet GraphQL is an archival fallback. Lookup is bounded to two pages per source and five candidate receipts, checks sender/success/TREE treasury credit, and sends candidates to the existing authenticated endpoint. The backend still independently enforces the exact offer, 20,000 TREE amount, checkpoint/expiry and single use. Public client lookup cannot grant lives. Old pending offers without the newly recorded start time use a two-hour search window. A transaction-ID entry remains inside a collapsed **Advanced payment recovery** disclosure as an optional fallback.

No server handlers, schema, treasury, amount, wallet setup or dependency lock were changed. This release preserves all 39 published backend package/provider/runtime/configuration records, all five schedules and every unrelated static path. The same explicit server-only isolated database binding and enabled-payment flag are retained. Only native game HTML/CSS and new native JavaScript assets change.

Validation: 24 focused checks, including actual React click interactions with a simulated wallet/server. Tests cover pay → waiting → verified Resume button → gameplay without typing a transaction ID; saved-offer discovery and resume without signing again; cancellation without gameplay; collapsed optional recovery; receipt mismatches; missing receipts; double clicks; lost responses; account switching; and the existing exact-price/recipient and recovery constraints. A read-only query also confirmed compatibility of the pinned SDK's mainnet transaction-list response; the old historical fixture was outside the bounded recent search. No real payment was signed or submitted by the assistant.
